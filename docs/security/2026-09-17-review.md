# Security review — 2026-09-17

Scope: the staging worktree's application code, actions, routes, authentication, billing, uploads, schema and migration sources, scripts, configuration, dependencies, and tests. This is a source review and local verification, not a certification of the live deployment. No production database was accessed, and no seed, reset, or database migration command was run.

## Resolved in this worktree

- Stripe reconciliation now grants Pro only for configured current or explicitly allowlisted legacy Price IDs. Checkout requires the webhook signing secret, checks customer ownership and existing subscriptions, and refuses an unrecognized app-origin subscription instead of risking another charge. Price rotations must retain prior Pro Price IDs in `STRIPE_PRO_LEGACY_PRICE_IDS` until those subscriptions end.
- OAuth-created email addresses are normalized, and existing-account lookups (including credential sign-in and registration) ignore case. Provider accounts still cannot silently attach to an existing keeper.
- Creating and restoring a spood serialize the Free-plan count and write under a user-row lock. A failed creation cleans up its uploaded Supabase object when possible.
- Care, activity, profile, settings, and Constellation writes have a durable daily account/IP limit. Server actions reject oversized text, excessive hydration methods, invalid molt phases, and invalid reminder intervals.
- The public health route no longer discloses which secrets and integrations are configured. Response caching is disabled. Global headers deny framing and MIME sniffing and limit browser permissions and referrer data.
- A patched `deepmerge-ts` version is installed through a package override. The full package audit reports zero known advisories.
- Landing copy no longer claims photos are private by default while uploads use public Storage URLs.

## Remaining security work and verification limits

1. **Production database exposure is unverified.** The original migration disables row-level security; a later hardening migration enables it and revokes browser-role table grants. Staging was previously checked with the Data API disabled and RLS/grants hardened. Because production access is prohibited, this review cannot establish whether production has the later migration or equivalent controls. A trusted production operator should verify Data API exposure, RLS, grants, and migration status without sharing credentials.
2. **Password signup does not prove email ownership.** Registration immediately activates an account for a syntactically valid address. Someone could claim another person's address and prevent its later use for signup or social sign-in. Resolving this needs a verified sender/domain, email delivery in the target environment, expiring one-use verification tokens, an unverified-account recovery path, and a rollout for existing accounts. Staging currently disallows a Resend key, so a safe end-to-end verification flow cannot be exercised there yet.
3. **Uploaded photos are public to anyone with their Storage URL.** The Privacy Policy discloses this, and app pages require a keeper session, but possession of a photo URL bypasses the app. Strict privacy would require a private bucket, authorized short-lived URLs or a guarded image route, and migration of existing objects/URLs.
4. **Billing still depends on webhook delivery.** A missed final event can leave a cached entitlement stale. Add a bounded scheduled reconciliation with authentication, retries, and alerts, and decide how long `past_due` should retain Pro. Stripe Billing Portal plan-switch options must be restricted to the intended Pro products/prices.
5. **Live integration behavior was not exercised here.** The Free-plan row-lock test uses a concurrent database double; no staging database writes or live Stripe/Meta calls were made. Facebook sign-in's previously reported provider error still needs a fresh end-to-end check after deployment.

These remaining items mean the application cannot yet be described as having *all* security issues resolved.
